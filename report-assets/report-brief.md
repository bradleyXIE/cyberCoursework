## Scenario (from the brief)
MSS Ltd, three departments: Marketing on floor 1 (20 workstations), Sales on floor 2 (25), General Support on floor 3 (15). Some applications move data between departments; each department mostly uses its own applications. Everyone needs Internet, intranet and e-mail. Each department has its own database of local information; all employees must be able to access any of these databases. A backup database server is needed. Assumptions in brief: departmental servers host applications and large data sets; an e-mail server; an intranet server; database and backup database servers; a backup/archive server; a redundancy plan for system failure; vulnerability analysis and maintenance; limited budget but willing to invest in quality.

## Design summary (what was built)
Architecture: collapsed core. Two Catalyst 3650-24PS multilayer switches (CORE-1, CORE-2, each with two AC power supplies) in a secure floor-1 server room (MDF). Four Catalyst 2960-24TT access switches in floor IDFs: ACC-F1-MKT (20 ports used), ACC-F2-SALES1 (13) and ACC-F2-SALES2 (12), ACC-F3-GS (15). Every access switch is dual-homed: Gi0/1 to CORE-1, Gi0/2 to CORE-2. The two cores are joined by an LACP EtherChannel (Port-channel1, Gi1/0/23–24). Two server-room switches DC-SW-A (services and data) and DC-SW-B (backup and management), each dual-homed to both cores. Two Cisco 2911 edge routers: EDGE-1 to ISP-A (primary), EDGE-2 to ISP-B (standby); each edge has a routed link to both cores. Two simulated ISP routers (2901) and a public web server represent the Internet (not MSS-owned).
Why collapsed core rather than three-tier: 60 users, one building, 3 floors – a separate distribution layer would add cost, devices and failure points without benefit; the two cores give device redundancy; growth path is to add access switches/stacks or a distribution pair later. Contrast with the "old/existing" collapsed design is not needed.
Why 2960 at access, 3650 at core: cost-effective fixed access switches where only L2 + security features are needed; L3 routing, HSRP, DHCP relay, ACLs and LACP only at the core; 3650 PoE+ ports and dual PSUs (PoE for future phones/APs). Packet Tracer limits: 2960-24TT used for access (24 FE + 2 GE uplinks) – in production the group recommends Catalyst 9200 access switches (see future proposition).
Ports: Marketing 20/24, Sales 25 across two switches (13+12) giving 23 spare ports on floor 2, GS 15/24 – about 40% spare access ports overall for growth. Unused ports are shut and placed in VLAN 999.

VLAN/IP plan: see design-tables.md. /24 per VLAN in 10.10.0.0/16 (RFC 1918) – room for growth (254 hosts per department vs 15–25 today) and simple, readable addressing (third octet = VLAN). Gateway .1 is an HSRP virtual IP; CORE-1 .2, CORE-2 .3.
Load sharing: CORE-1 is HSRP active and STP root for VLANs 10/30/50/99; CORE-2 for 20/40/60 (priority 110 vs 100, preempt; STP priority 4096 vs 8192). Cores also root for VLANs 900 and 999 so root guard does not block downlinks.
Routing: OSPF area 0 with MD5 authentication on all routed links (cores, edges, core-to-core transit VLAN 900 over Po1). passive-interface default. Only EDGE-1 originates the default route into OSPF; each core also has a floating static default (AD 250) towards EDGE-2. Packet Tracer limitation: IP SLA/object tracking is not available on the 2911 image, and Packet Tracer ignored OSPF default metrics, so the floating static design was chosen and tested. Production recommendation: IP SLA tracking of the ISP path.
NAT: PAT on each edge (access-list 1 = 10.10.0.0/16, overload on Gi0/2). OUTSIDE-IN ACL on WAN: anti-spoofing (RFC 1918 and loopback sources dropped), permits only established TCP, echo-reply and unreachable; all else denied.
DHCP: centralised DHCP with relay – both cores relay (ip helper-address) to two DHCP servers: INTRANET leases .11–.130 and MAIL leases .131–.250 of each user VLAN. Either server or either core can fail and clients still get addresses. Decision note: an initial split-scope on the cores was rejected after testing because Packet Tracer's IOS DHCP honoured only one excluded-address range per subnet, causing overlapping scopes (found and fixed during testing – good example of testing-driven design).
DNS: INTRANET primary, MAIL secondary; records intranet/mail/db-marketing/db-sales/db-support.mss.lan, www.public.test.
Servers (see table): INTRANET (HTTPS only), MAIL (SMTP/POP3), DB-MKT, DB-SALES, DB-GS (department application + database servers in DATA VLAN 50, HTTPS front end), DB-REPLICA (backup database server, VLAN 60), BACKUP-ARCHIVE (backup/archive FTP target, VLAN 60), NMS (syslog, NTP, RADIUS AAA, VLAN 99), ADMIN-PC (VLAN 99). Primary data servers on DC-SW-A/Rack A, replica + archive on DC-SW-B/Rack B: a single rack, switch or power-feed failure cannot take out both a database and its copy. Unused server services (FTP default account, HTTP, DHCP, DNS etc.) disabled on every server.

Security controls (defence in depth):
- Segmentation: 9 VLANs; inter-VLAN policy enforced on both cores with named ACLs (see design-tables.md). USERS-IN: users may reach DNS, HTTPS intranet, SMTP/POP3 mail, HTTPS on all departmental DB servers (requirement: everyone can access every department database), ping for support, and the Internet; denied: backup VLAN 60, management VLAN 99, infrastructure, direct host-to-host traffic between departments (data sharing between departments goes through the departmental servers), plain HTTP to intranet. BACKUP-OUT: only data, services and management networks may reach backup. MGMT-OUT: only return traffic and syslog/NTP/RADIUS reach the management VLAN.
- Access layer: port-security (max 2 MACs, sticky, violation restrict) on workstation ports, max 1 on server ports; PortFast + BPDU guard on edge ports; DHCP snooping (uplinks trusted, 20 pps limit) and Dynamic ARP Inspection on user VLANs; trunks with native VLAN 999, explicit allowed VLAN lists (pruning), DTP disabled (nonegotiate); unused ports shut in VLAN 999; CDP disabled on user ports and the WAN.
- STP: rapid-PVST, root placement aligned with HSRP, root guard on core downlinks.
- Device hardening: SSH v2 only (RSA 2048), VTY restricted to VLAN 99 by access-class, AAA with RADIUS (NMS) and local fallback, console local authentication, enable secret + service password-encryption, login block-for 120 after 3 failures in 60 s on routers/cores, exec timeouts, legal banner, HTTP server disabled, NTP and syslog to NMS, OSPF MD5.
- Edge: PAT hides internal addressing; inbound ACL permits only replies.

Redundancy summary: dual cores (HSRP), dual uplinks per access/DC switch, LACP between cores, dual PSUs in cores, dual edge routers and dual ISPs, two DHCP/DNS servers, database replica in separate rack/switch. Remaining single points of failure (be honest): each access switch (users on one floor switch lose access if it fails – mitigated by spare switch / stacking in future), each server's single NIC in PT, the public Internet simulation.

Cabling (proposed): horizontal Cat6 U/UTP from desk outlets to the floor IDF (≤90 m permanent link per TIA-568), patch panels in each IDF; riser: two physically separate riser routes per floor (Riser A to CORE-1, Riser B to CORE-2), recommended OM4 multimode fibre with 1G/10G SFP for future 10G; in Packet Tracer the 2960-24TT copper Gigabit uplinks are used as the equivalent. Server-room patching Cat6A short patch leads; ISP-A and ISP-B enter via separate building ducts. Labelling scheme: <room>-<rack>-<panel>-<port> on both ends; colour coding by VLAN class. Rooms: floor 1 secure server room (badge access, UPS, A/B power feeds) holds Rack A (CORE-1, EDGE-1, DC-SW-A, primary servers) and Rack B (CORE-2, EDGE-2, DC-SW-B, replica/archive, NMS). ## Vulnerability analysis – evidence (Docker lab with Kali tools, 25 Nov 2026 rerun, PASS)
Lab: disposable Docker containers on internal bridges, no published ports, synthetic data only. Kali container 172.29.216.10 represents an employee host on a user VLAN; intranet web app 172.29.216.30 (Python); PostgreSQL 16 backup database 172.29.217.20 on a protected bridge; in the baseline the backup DB is also attached to the employee bridge as 172.29.216.20 (models a flat network / missing ACL). Tool versions: Nmap 7.991, curl 8.22.0 (OpenSSL 3.6.5), tcpdump 4.99.6, Python 3.12.3, PostgreSQL 16.15, Docker 29.9.2.
Baseline findings:
 V1 Exposed backup database: `nmap -sT -sV -Pn -p 5432 172.29.216.20` → 5432/tcp open postgresql (E01).
 V2 Cleartext credentials: intranet on HTTP 8080 (`nmap` shows 8080 open BaseHTTPServer, 8443 closed); tcpdump capture shows "Authorization: Bearer LAB-EMPLOYEE-ONLY" in readable form (E03).
 V3 Broken access control: employee token can call /admin/export → HTTP 200 (E02); anonymous gets 401.
Hardened (mirrors the PT design: backup VLAN isolation, HTTPS-only intranet, role checks):
 V1 fixed: 5432 from employee network filtered (no-response / net-unreach); positive control from backup network shows 5432 open (E05) – service still works where it should.
 V2 fixed: 8080 closed, 8443 open ssl/http; TLS 1.3 TLS_AES_256_GCM_SHA384, certificate subject CN=intranet.lab matches; wrong hostname rejected (curl exit 60); capture no longer contains the bearer token (E06–E08).
 V3 fixed: employee export → 403 "administrator role required"; admin → 200 (E06).
Additional vulnerabilities to discuss for the MSS design (analysis + tools, not all executed): VLAN hopping/DTP & native VLAN (mitigated: nonegotiate, native 999, pruning) – Yersinia; rogue DHCP / DHCP starvation – Yersinia, dhcpstarv (mitigated: DHCP snooping, rate limit, port-security); ARP spoofing/MITM – arpspoof/Ettercap/Bettercap (mitigated: DAI, TLS); MAC flooding – macof (port-security); STP root takeover (BPDU guard, root guard); brute force of SSH/RADIUS/mail/FTP – Hydra (login block-for, VTY ACL, strong secrets, RADIUS; FTP/POP3 cleartext is a residual risk → SFTP/IMAPS/POP3S future); weak/legacy services – Nmap NSE (ssl-enum-ciphers), Nikto, OpenVAS/Greenbone for authenticated vulnerability scanning; web app – OWASP ZAP / Burp Suite; password audit of hashes – John the Ripper / Hashcat (type 5 MD5 enable/username secrets visible in PT → recommend type 8/9 scrypt on real IOS); OSPF/HSRP spoofing (MD5 auth; HSRP authentication recommended in production); Internet-facing – nmap from outside against 203.0.113.2 (only replies permitted); Windows tools: Wireshark, Nmap/Zenmap, PuTTY, Microsoft Baseline/Defender? (avoid claims about obsolete MBSA; can mention Nessus Essentials).
Defence mechanisms must tie back to findings. Maintenance guideline: schedule (e.g. monthly authenticated scan, quarterly internal pentest, after every change: rerun the automated lab/verification and check_config drift check), patching IOS/servers, config backups, log review (syslog NMS), access reviews, backup restore tests (replica), change control, rules of engagement/authorisation (only in-scope, written permission, NIST SP 800-115 phases).
